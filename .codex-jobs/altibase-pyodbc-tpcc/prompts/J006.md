# Job J006: pyodbc/native comparison runs

## Goal

Run comparable TPC-C smoke/performance checks for the pyodbc and native Altibase backends, capture the result metrics, and document how to repeat the comparison.

## Source Material

- `ALTIBASE_PYODBC_EXECUTION_DESIGN.md`
- `ALTIBASE_TEST_NOTES.md`
- `pytpcc/ALTIBASE_ODBC_EXAMPLE`
- `pytpcc/ALTIBASE_NATIVE_EXAMPLE`
- `pytpcc/tpcc_altibase.sql`
- `pytpcc/util/results.py`
- `pytpcc/results.log` behavior, if relevant

## Scope

- Run both backends through the same `altibase` target and the same DDL.
- Use the same warehouse count, scale factor, duration, client count, Altibase server, and schema credentials for both runs.
- Capture comparable output: tpmC or transaction throughput, transaction counts, abort counts, retry counts, elapsed duration, and any backend-specific warning.
- Add or update concise documentation with repeatable commands and a small result table.
- Do not treat this as an official TPC-C benchmark certification.
- Do not commit raw logs, credentials, generated DB dumps, or workflow runtime files.
- This job is not complete unless both pyodbc and native measured runs succeed under the same scale, duration, client count, schema credentials, and server. If either backend cannot run, stop with a clear failure instead of marking `J006` as `Done`.

## Required Implementation

1. Read the source material and inspect the result output format before running comparison commands.
2. Confirm that both configs target the same schema credentials. If they do not, either align them or document why the comparison is not apples-to-apples.
3. Before each measured run, reset and load the schema with the backend being measured unless the implementation proves that execute-only reuse is fair and identical.
4. Use a small repeatable baseline first:
   - `warehouses = 1`
   - `scalefactor = 100`
   - `clients = 1`
   - `duration = 30`
5. If the 30-second run is stable for both backends and time allows, optionally add a second comparison at `duration = 60` or `clients = 2`, but do not expand scope if the baseline is still unstable.
6. Keep pyodbc and native environment setup explicit:
   - pyodbc requires `ALTIBASE_HOME`, `ALTIBASE_PORT_NO`, `LD_LIBRARY_PATH`, and DSN `ALTIBASE_LOCAL`.
   - native requires the same Altibase runtime variables plus `PYTHONPATH=/home/et16/work/altibase-python-driver/src`.
7. If either backend fails, preserve enough error detail in the documentation to make the failure reproducible, then leave the job incomplete or mark it `Fail`; do not commit `J006` as `Done`.
8. Review whether result summaries clearly distinguish the backend. If output only says `AltibaseDriver`, add a narrow summary label or documentation note so pyodbc/native results cannot be confused.
9. If local credentials are unavailable, do not fake performance data and do not mark `J006` as `Done`. Document the exact blocked condition and leave repeatable commands for the next run.
